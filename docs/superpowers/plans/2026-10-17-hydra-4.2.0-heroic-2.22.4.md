# Hydra 4.2.0 and Heroic 2.22.4 in the official bundle (0.4.2): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bundle 0.4.2 lists Hydra 4.2.0 and Heroic 2.22.4 as stable versions, so `revamp update` installs them without `--force`; Hydra 4.1.6 and Heroic 2.22.3 stay listed.

**Architecture:** Nothing in the patches changes: the released bundle already applies 7/7 to Hydra 4.2.0 and 3/3 to Heroic 2.22.4 in a forced dry run, and every fingerprinted region of both new builds is byte-identical to the listed one. The work is listing the versions with their verified SHA-256, widening each patch's `compatibleWith`, adding trimmed fixtures of the new builds, and running the existing unit and integration tests over every listed version instead of one. Then the usual release.

**Tech Stack:** Node 26.12 (type stripping), `node --test`, `@revamp-app/{sdk,engine,cli}` 0.3.0 from npm (unchanged), `@electron/asar` (tests), `gh`.

**Spec:** Revamp's `docs/superpowers/specs/2026-10-14-revamp-v1-design.md`: §5.1 (versions and release hashes), §5.5 (a patch incompatible with the version is excluded unless `--force`), §7.4 (CI dry-runs every listed version), §13 M2 (how Heroic 2.22.3 and the forced-version check were added; Revamp's `docs/superpowers/plans/2026-10-14-revamp-m2-breadth.md` Tasks 8 and 9). The work order is https://github.com/xb00tt/revamp-patches/issues/1 (it names `bundles/official/…` paths and 0.5.0 from before the split; the paths are this repo's and the version is 0.4.2, since the patches are unchanged). Release steps: this repo's `CLAUDE.md`, "Releases".

- Work on branch `hydra-4.2.0-heroic-2.22.4` in `/home/borislav/github/revamp-patches` itself (no other session works there; the owner's `AGENTS.md` convention is Revamp's, not this repo's). Never force-push.

- Pushing, opening and merging the PR, `npm run release`, `git push` of the release commit, and anything on the owner's machine (`revamp check`, `revamp update`) each wait for the owner's go-ahead in chat. Progress and findings go to issue #1 as comments; the PR closes it.

## Review Focus

1. **A user on Hydra 4.1.6 runs `revamp update`:** the newest listed stable version (`newestStable`) is now 4.2.0, so the update installs it without `--force` and every patch applies. The integration test in Task 2 installs 4.2.0 from the built bundle; `patchApp` without `version` (the second Hydra integration test) now also runs on 4.2.0.
2. **Hydra 4.2.0's 1,048 symlinks:** a real install, not just a dry run, must create them inside `apps/hydra/4.2.0/` and the app must still launch from `current`. Task 2's 4.2.0 install test covers the install; the owner's machine step (Task 4) covers the launch.
3. **Big Picture untouched on 4.2.0:** the two slice hashes are re-measured on the stock 4.2.0 renderer (above) and pinned per version in Task 2, so a patch that drifted into Big Picture fails the test.
4. **A fixture that drifts from the real build:** every non-trimmed line of each new fixture must occur verbatim in the real 4.2.0 or 2.22.4 file. Task 1 Step 1 checks this with the same script the planning session ran.
5. **CI's matrix:** `patches.json` now has four stable versions, so the push runs four `dry-run` jobs, each downloading its release once into the Actions cache (Task 4 watches them before merging).
